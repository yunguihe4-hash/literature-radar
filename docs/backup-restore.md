# SQLite backup, restore and upgrade

`literature-radar backup --database STATE_DB --output NEW_BACKUP_DB` uses the
SQLite Backup API and runs an integrity check. The destination must not
exist. `literature-radar restore --backup BACKUP_DB --output NEW_STATE_DB`
also creates a new, verified database; it never replaces an existing one.
These operations preserve both legacy paper keys and the additive production
event, notification and schedule tables.

Feedback, Attention Memory, Topic configuration and workflow state are JSON
files outside SQLite. Back them up separately into a private directory with
mode 700, using unique destination names and mode 600 for files. Verify their
SHA256 hashes and validate a restored copy with `topic validate` and
`feedback summary` before relying on it. Never place a private backup in the
source checkout, release wheel or public repository. Restore into new paths;
retain the previous database and JSON files until the restored workflow has
been checked together. SQLite backup alone is not a complete user-state
backup.

Before upgrading, stop scheduled invocations, create a backup, and verify it
by restoring to an independent temporary path. Install the new wheel into a
new virtual environment. Run configuration validation and the offline
synthetic workflow, then point the runtime command at the existing private
configuration and database. If the upgrade fails, stop the new command and
restore the previous environment and database path from the verified backup.
Never overwrite user configuration or database files as part of wheel
installation.

The 0.1.0 validator does not recognize the `direct_reference` ontology type
generated by 0.2.x Topic initialization. A rollback to 0.1.0 therefore
requires the matching pre-upgrade configuration snapshot as well as the
pre-upgrade SQLite backup. Do not point 0.1.0 at a newly initialized 0.2.x
Topic. This compatibility boundary should be checked before any production
upgrade.

SQLite `PRAGMA user_version` remains 2 for compatibility with existing
callers. Additive production tables are recorded by the
`schema_features.production_events` marker at version 3. The application
creates these tables transactionally on first open; it does not drop legacy
tables. Keep the backup until the upgraded installation and rollback rehearsal
have been verified.
